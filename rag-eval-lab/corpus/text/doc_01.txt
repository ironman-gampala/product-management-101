PHASE 0 - FOUNDATIONS
What AI - and an LLM - actually is
Goal: stop sounding like "AI magic" and start sounding like someone who ships AI inside a

0A - What kind of intelligence is this
Foundational
Ground-Up Roadmap
The nesting: AI -> ML -> DL -> GenAI -> LLM
WHAT THIS LOOKS LIKE

ARTIFICIAL INTELLIGENCE
any system doing "intelligent" tasks - rules included
 ↓ contains
MACHINE LEARNING
learns patterns from data
 ↓ contains
DEEP LEARNING
many-layered neural nets
 ↓ contains

 ↓ contains
LARGE LANGUAGE MODELS

Each box only lives inside the one above it. Prodigy's validation engine is AI, not ML - a hand-written rule. Prodigy's chat is all
five boxes deep.
PLAIN ENGLISH
Artificial intelligence is the broad goal of machines doing useful "intelligent" work - including
hand-written rules. Machine learning is AI that learns patterns from data instead of being explicitly
programmed. Deep learning is ML using many-layered neural networks. Generative AI is deep learning
that produces new content instead of a label or a number. Large language models are generative
models specialised in text - predicting the next token, steerable with prompts, tools, and retrieval.
ANALOGY
Nested boxes: transport -> motor vehicles -> cars -> electric cars -> Teslas. Every Tesla is an electric
car; not every motor vehicle is. When a vendor says "we use AI," they've told you as much as "we use
transport" - the useful question is which box down the stack they're actually in.

CONCRETE EXAMPLE
Four systems in one bank: a rules engine that flags any transaction over $10,000 (AI, no learning) - a
gradient-boosted model predicting which cards will default (classical ML, not deep learning) - a neural
net reading scanned KYC documents (deep learning, discriminative) - Prodigy drafting a
change-request summary (LLM, all the way down the stack). All four are legitimately "AI." Only one
needs a GPU bill and a context window.
In Prodigy
Prodigy sits on Product Center, a system of record. The LLM is the language and planning layer; blueprints,
fields, entitlements, and the CR workflow remain non-negotiable product contracts - not model opinions.
Interview one-liner
"LLMs are a generative subset of AI; in Prodigy they compose and plan, but schema and services remain the
source of truth."

Supervised, unsupervised, and reinforcement learning
PLAIN ENGLISH
Supervised learns from labelled examples ("here are 50,000 emails marked spam / not spam").
Unsupervised finds structure with no labels ("here are 50,000 customers - what natural groups
exist?"). Reinforcement learns from trial, reward, and penalty. Modern LLMs use all three in
sequence: unsupervised pre-training on huge text, supervised fine-tuning on curated examples, then
reinforcement learning from human feedback (RLHF) to align tone and safety.
ANALOGY

Supervised is a tutor marking your homework. Unsupervised is sorting a box of mixed photos into piles
with no labels provided. Reinforcement is learning to ride a bike - no one tells you the exact muscle
sequence, only whether you fell over.
CONCRETE EXAMPLE
Product Center's validation framework (SPI-24209) is a supervised, rules-based classifier in spirit:
fixed labels ("blocks release" / "warns" / "passes") applied deterministically. When Prodigy explains
why a fee is out of range in plain language, that explanation layer is generative - but the pass/fail
decision underneath is not learned at all; it's a rule.
In Prodigy
Validation is deterministic (supervised-style rules, hand-authored). The NLP summary layer on top is
generative. Never let the generative layer decide the pass/fail - that's the classic AI-PM failure mode.
Interview one-liner
"I know the difference between a system that learned a decision boundary and one that generates an
explanation of a hand-written rule - and I never let the second one pretend to be the first."
New in this rework
Parameters, weights, and "the model"
PLAIN ENGLISH
A model is, physically, a very large file of numbers called parameters (or weights). Architecture defines
how those numbers are arranged and combined; training finds good values for them. A
"70-billion-parameter model" is literally 70 billion numbers. There is no database of facts inside - no
lookup table of your fee schedule.

ANALOGY
A weights file is like a chef's trained palate, not a recipe book. The chef can improvise a plausible dish
from anything you describe - but if you want an exact recipe from your own kitchen, you hand them the
actual card (retrieval / tools), you don't trust their memory of "a dish kind of like this."
CONCRETE EXAMPLE
Ask a raw model "What is Regalia Gold US's joining fee?" and it will confidently guess a plausible
number - because that number was never in its weights. Ask the same question through Prodigy's
Path 3 (cited Q&A), and the tool call fetches the real value from Product Center / GitDB; the model
only phrases the sentence around it.
In Prodigy
Every product-specific fact must come from a tool call or a citation, never from weights. This is the entire
reason ToolRegistry and grounding exist.
Interview one-liner
"Weights are a trained palate, not a filing cabinet - anything customer- or product-specific has to be retrieved,
not recalled."
Prodigy-native
Training vs. inference (why chatting doesn't teach Prodigy)
WHAT EACH PROCESS LOOKS LIKE
TRAINING (HAPPENS ONCE, OFFLINE)
 Huge dataset
 Expensive compute, days/weeks

Weights permanently updated
INFERENCE (HAPPENS EVERY CHAT)
 Alex's message this turn
 Frozen weights + tools + context
 One answer, weights unchanged
Alex correcting a fee in chat is the right-hand column, every time - nothing on the left ever runs during a normal conversation.
PLAIN ENGLISH
Training updates model weights using large datasets and expensive compute. Inference is using a
frozen (or lightly adapted) model to generate outputs for a request. When Alex chats with Prodigy, he
is doing inference. The model does not permanently learn Regalia Gold's fee from that conversation
unless you build an explicit memory or data pipeline - and even then you're writing to your own
systems, not "retraining GPT."
ANALOGY
Training is rewriting the textbook. Inference is a student answering today's exam using the textbook
plus the open-book materials you hand them (tools, schema, retrieval).
CONCRETE EXAMPLE
Alex corrects "joining fee is $95, not $90." Confirm patches the form / draft. Future answers should
come from Product Center state, not from the model's vibes about yesterday's chat. Conversation
history helps continuity; it is not a weight update.
In Prodigy

Never tell an interviewer "the agent learns from our users" without specifying session memory, eval datasets,
fine-tunes, or preference data - and the governance around each.
Interview one-liner
"User chat is inference against tools and schema; learning happens through product data and deliberate
eval/train loops, not by osmosis."

The whiteboard is full. Page-aware context engineering means the schema and tool result stay pinned every turn - old chat

PLAIN ENGLISH
Models don't read "words" the way you do - text is broken into tokens (subword pieces). The context
window is the maximum tokens the model can attend to in one call: instructions, history, tool results,
and schema snippets all compete for that budget. Exceed it and something gets truncated or
summarized away.
ANALOGY

A whiteboard with a fixed size. Skills, page context ("Fees tab open"), conversation history, and tool
outputs all fight for marker space. When the board fills up, earlier notes get erased.
CONCRETE EXAMPLE
Guided configuration on a fat blueprint: dump the entire schema, full MITC text, and twenty turns of
chat into one call and you blow the window - the model misses a required field. Product design must
choose what's pinned (schema for the active tab), what's retrieved on demand (a lookup list), and
what's summarized.
In Prodigy
Page-aware Prodigy is a context-engineering product: pass page, product, blueprint, active tab, and session
id into the skill - don't force Alex to restate what's on screen.
Interview one-liner
"Context is a scarce product resource; we design what the agent sees, not just what the user types."

Embeddings - meaning as coordinates
WHAT AN EMBEDDING SPACE LOOKS LIKE
"joining fee"
"annual fee waiver"
"no yearly charge"

"credit limit"
"spend cap"
fee-related meaning cluster
credit-limit meaning cluster
"Annual fee waiver" and "no yearly charge" share no words but land close together - because embeddings encode meaning,
not spelling. Keyword search would miss this; embeddings wouldn't.
PLAIN ENGLISH
An embedding turns a piece of text into a list of numbers (a vector) positioned in a high-dimensional
space, such that texts with similar meaning land near each other - even if they share no words. This is
the foundation for search, recommendation, clustering, and retrieval-augmented generation (RAG).
ANALOGY
Think of a giant map where every sentence gets a pin. "Annual fee waiver" and "no yearly charge" get
pinned close together even though they don't share a word - because they mean roughly the same
thing. Keyword search would put them on opposite sides of the map; embeddings put them next to
each other.
CONCRETE EXAMPLE
If Prodigy ever needs to find "which existing product is most like the one Alex is describing" for
clone-and-merge (SPI-24207), embeddings are how you'd compare a free-text description against
product summaries - not by matching keywords, but by matching meaning.
In Prodigy
Today, clone-and-merge uses explicit product selection (Alex picks the product), which is simpler and more
auditable than semantic search. Embeddings become relevant if you ever build "find me a similar product" as
a suggestion feature.

Interview one-liner
"Embeddings let us search by meaning instead of by keyword - the substrate under RAG, semantic
clone-suggestion, and dedup."

Transformers and attention
WHAT ATTENTION LOOKS LIKE WHEN ANSWERING "WHAT'S THE JOINING FEE?"
Regalia
Gold
joining
fee
is
?
Bar height = how much weight the model gives each token while generating its answer. "Joining" and "fee" dominate; "is" and
"?" barely register. This re-weighting, done per token, is what "attention" means.
PLAIN ENGLISH
The transformer is the architecture that made today's LLMs possible. Its key trick is attention: for
every token being generated, the model computes how much "weight" to give every other token in
context, so it can decide what actually matters right now instead of reading everything with equal
importance.
ANALOGY
Attention is like a courtroom where every witness statement gets weighed differently for each specific
question - the same testimony matters a lot for one question and almost nothing for another. The
model re-weighs the whole room for every word it writes.
CONCRETE EXAMPLE

When Alex asks "what's still missing on the Fees tab?", attention is why the model can pull from the
schema tool result (this tab's fields) far more heavily than from an unrelated earlier turn about the
Rewards tab - as long as both are still inside the context window.
In Prodigy
You don't need to implement attention - you need to know it exists so you can reason about why irrelevant
context (a stale 20-turn-old message) can still distract the model, and why keeping context tight and
well-labeled genuinely improves accuracy.
Interview one-liner
"I don't train transformers, but I know attention is why context hygiene is a product lever, not just an
engineering nicety."
Prodigy-native
Non-determinism and sampling
PLAIN ENGLISH
Given the same prompt, an LLM can produce different outputs because decoding samples from a
probability distribution (temperature, top-p, etc). Even at temperature 0, ties and infrastructure variance
can surprise you. Treat outputs as proposals, not database writes.
ANALOGY
Ask three analysts the same open question and you get three wordings. If your bank needs one fee
value, you don't let three analysts write the ledger - you pick a process that confirms a single value.
CONCRETE EXAMPLE

Alex says "set joining fee to something reasonable." Two runs may suggest $95 and $100. That's fine
as a suggestion. It's unacceptable as an unsupervised write. Confirm-before-write and schema enums
collapse the ambiguity.
In Prodigy
Non-determinism is why Prodigy separates propose vs. confirm, why evals use golden conversations with
tolerances, and why the validation framework is deterministic while NLP summaries can be generative.
Interview one-liner
"We assume the model will vary; product safety comes from confirmation, schema, and deterministic
validators - not from hoping temperature is zero."
Prodigy-native
Prompting vs. context engineering
PLAIN ENGLISH
Prompting is writing instructions for one call. Context engineering is the system design of everything
the model sees over time: skills, retrieved facts, tool results, entitlements, page state, conversation
memory, and what's deliberately withheld. Mature products win on context engineering, not witty
system prompts.
ANALOGY
Prompting is writing a sticky note. Context engineering is designing the entire briefing pack: which
docs, which APIs, which permissions, which prior decisions, which red lines.
CONCRETE EXAMPLE

A clever prompt saying "always use schema" fails if the schema isn't in context and there's no tool to
load it. The durable fix is a ToolRegistry call that loads tabs, fields, enums, and conditionals for the
blueprint - then a skill that says confirm before patch.
In Prodigy
Skills are context-engineering artefacts: name, description, procedure, confirmation points, pinned version.
They guide procedure; they don't invent product rules or grant access.
Interview one-liner
"I treat skills and tool results as the real product surface; prompts are the thin instruction layer on top."

Ground-Up Roadmap
When classical ML still wins
PLAIN ENGLISH
LLMs are expensive, slow, and non-deterministic relative to a simple rule or a small classical model. If
the input is structured, the answer needs to be exact, and the decision boundary is learnable from
tabular data, a rules engine or gradient-boosted model usually beats an LLM on cost, latency, and
auditability.
ANALOGY
You don't call a consultant to check if a number is bigger than a threshold. A calculator is faster,
cheaper, and never hallucinates.
CONCRETE EXAMPLE

"Is this late fee within the legally allowed range?" is a deterministic comparison against a rule table -
exactly what Prodigy's validation framework does. Routing that question to an LLM would be slower,
costlier, and occasionally wrong. The LLM's job is to explain the verdict in plain language, not compute
it.
In Prodigy
The entire "schema is law, validation is deterministic, LLM explains" design is a direct application of this
principle at product scale.
Interview one-liner
"Being a good AI PM means knowing when to say no to an LLM - the validation engine in Prodigy is
deliberately not one."

PHASE 1 - FROM CHATBOT TO AGENT
Chatbot, workflow, or agent - and how to decide

Goal: a repeatable decision framework you can defend under pressure, not a vibe.
AI PM must-know
Chatbot vs. workflow vs. agent
WHAT EACH ONE LOOKS LIKE END TO END
CHATBOT
 "What's the fee?"
 one lookup
 answer
WORKFLOW
 fee submitted
 fixed rule checks
 pass / block, same every time
AGENT
 "launch a card from this PDF"
 unknown # of tool calls
 draft, then confirm
The number and order of steps is fixed for a workflow, one-shot for a chatbot, and decided by the model, step by step for an
agent.

PLAIN ENGLISH
A chatbot converses but doesn't reliably operate tools across multiple steps. A workflow is a fixed,
deterministic sequence - same input, same path, every time. An agent is a goal-seeking loop: it
decides which tool to call next based on what it observes, under uncertainty, until a goal or stop
condition is met.
ANALOGY
A chatbot is a knowledgeable receptionist. A workflow is a factory conveyor belt. An agent is a project
manager who improvises the next step based on what just happened, but still reports to a boss before
signing anything.
CONCRETE EXAMPLE
"What's Regalia Gold's joining fee?" -> chatbot-shaped (one lookup, answer). "Every fee change
needs the same five validation checks" -> workflow-shaped (fixed, deterministic). "Launch a credit card
in the US from this MITC PDF" -> agent-shaped (unknown number of steps, tool choices, and
clarifying questions).
In Prodigy
Path 3 (cited Q&A) is chatbot-shaped. The validation framework is workflow-shaped. Path 1 (launch) is
agent-shaped - that's exactly why it needs a full skill, not a prompt.
Interview one-liner
"I use a simple test: is the path fixed, is the write dangerous, is language the interface? That tells me chatbot,
workflow, or agent."

Every "agentic" Prodigy feature is this same four-step loop with a different goal, a different tool set, and different stop

PLAIN ENGLISH
Goal -> think -> act (call a tool) -> observe (read the result) -> repeat, until the goal is reached or a
stop condition fires. Every "agentic" feature is this loop with different tools and different stop conditions.
ANALOGY
A detective: form a hypothesis, go check one clue, update the theory based on what you found, decide
whether to check another clue or close the case.
CONCRETE EXAMPLE
Guided configuration: goal = "complete the Fees tab" -> think "what's still empty?" -> act: call schema
tool -> observe: three required fields remain -> ask Alex or propose from context -> repeat until the tab
is complete or Alex exits.
In Prodigy
The loop runs inside a skill with a bounded tool set (ToolRegistry entries for that skill only) and hard stop
conditions: max turns, confirmation required before any write, and no autonomous CR submission.
Interview one-liner

"An agent in our product is a bounded loop - not an open-ended chatbot with production keys."
AI PM must-know
Limits and stop conditions
PLAIN ENGLISH
An agent left unbounded can loop forever, spend unbounded tokens, or take unbounded time. Product
design must set: max turns, max tool calls, wall-clock timeout, and "fail closed" behaviour (deny rather
than guess) when something goes wrong.
ANALOGY
A test drive has a mileage cap and a return time - not because the car is untrustworthy, but because
unbounded trust is bad design regardless of trust level.
CONCRETE EXAMPLE
If Alex's document upload fails to parse cleanly, the skill should stop and show a confirm board with
partial results - not retry indefinitely or silently invent the missing fields.
In Prodigy
Runtime controls in the architecture decision explicitly limit turns, duration, tool-call time, and output tokens,
and disable parallel tool calls - this is a named, deliberate control, not an afterthought.
Interview one-liner
"Stop conditions are a product requirement I write into the spec, not an engineering default I hope exists."

AI PM must-know
When NOT to use an agent
PLAIN ENGLISH
If the steps are always the same, if the answer must be exact and auditable, or if the "intelligence"
needed is just a lookup - don't reach for an agent. Agents add latency, cost, and failure surface for
problems a form or a rule already solves.
ANALOGY
You don't hire a consultant to alphabetize a list.
CONCRETE EXAMPLE
"What's currently live for this product?" doesn't need an agent loop - one grounded lookup and a
citation is enough. Turning it into a multi-step agent just adds latency and more places for it to go
wrong.
In Prodigy
Path 3 deliberately stays close to a single grounded lookup with citations, not a multi-turn agent - it hands off
to Path 2 only if Alex decides to change something.
Interview one-liner
"Half of being a good AI PM is knowing which features should not be agentic."

PLAIN ENGLISH
A human must approve any action with real consequence before it takes effect. In practice: the model
proposes, a person confirms, and - separately - a person deploys. Two different gates, not one.
ANALOGY
A junior analyst can draft a wire transfer; only a manager's signature releases the money - and a

CONCRETE EXAMPLE
Prodigy proposes "$150" for the annual fee. Alex confirms it into the draft form. That draft still has to
pass CR review, validation, and dry run before a human deploys it in Product Center.
In Prodigy

or apply a change; only the existing change-and-approval flow can.

Interview one-liner
"Confirm and deploy are two separate gates by design - a model proposing something is never the same
event as production changing."

PHASE 2 - SKILLS, TOOLS, MCP & APPLIED ARCHITECTURES

Goal: explain how raw models become systems that know your data, call your tools, and
complete multi-step work - using the real Product Center AI architecture as the case study.
Prodigy-native
Skills (the Agent Skills standard)
WHAT A SKILL ACTUALLY LOOKS LIKE (GUIDED CONFIGURATION)
Name + description
"Guided configuration - walk Alex through empty required fields"
Required tools
get_schema, get_lookup, propose_field - nothing else
Procedure
load schema -> ask/propose per field -> next field
Confirmation points
pause before any field is written

Notice what's missing: no fee ranges, no access rules. A skill is a checklist of steps and pauses - the actual product rules live
in the tools and services it calls, not in the skill itself.
PLAIN ENGLISH
A skill is a version-controlled procedure: name, description, the steps to follow, required tools,
confirmation points, and context requirements. Skills guide the model through a named job. They do
not grant access and do not define product rules - those live in the services the skill calls.
ANALOGY
A skill is a pilot's checklist, not the plane's engine and not the pilot's licence. It tells you the order of
steps and where to pause for a second signature; it doesn't grant you the right to fly or change how the
engine works.
CONCRETE EXAMPLE

Two front doors, one ToolRegistry and one set of services behind them. MCP is not a second business-logic path - it's how a

PLAIN ENGLISH
MCP is a standard protocol so any agent harness - not just your own app - can discover and call a

custom integration per pair.
CONCRETE EXAMPLE

the same "propose a fee change" tool Prodigy uses inside Product Center - same rules, same audit
trail, different front door.
In Prodigy
Product Center Service exposes an MCP API using MCP 2026-07-28 over Streamable HTTP, publishing
OAuth protected-resource metadata - for external agent harnesses, separate from the embedded chat's AI
REST API, but sharing the same ToolRegistry contracts and handlers underneath.
Interview one-liner
"MCP isn't a second source of truth - it's a second front door onto the same tool contracts, for harnesses we
don't control."

RAG - Retrieval-Augmented Generation
WHAT THE PIPELINE LOOKS LIKE FOR AN UPLOADED MITC PDF
MITC PDF
->
Chunk into clauses
->
Embed each chunk
->
Retrieve relevant chunk for "joining fee"
->
Propose value + show source clause on confirm board
Every proposal traces back to the exact chunk it came from - that traceability is what makes RAG safe to show Alex, instead of
a paraphrase with no source.
PLAIN ENGLISH
RAG means: before (or during) generation, fetch relevant chunks of your own data and put them in
context, so the model answers from your facts instead of its trained-in guesses. The pipeline is usually:
chunk documents -> embed chunks -> store vectors -> embed the query -> retrieve the nearest
chunks -> stuff them into the prompt -> generate, ideally with citations back to the source.
ANALOGY

An open-book exam. The student (the model) is smart at writing, but you still hand them the exact
textbook page before they answer - you don't trust them to remember your specific numbers from
memory.
CONCRETE EXAMPLE
Parsing an uploaded MITC PDF (SPI-24282) is retrieval-shaped even without a vector database:
extract the relevant clause, put it in context, propose a field value, and show a confirm board that
traces each proposal back to the source text.
In Prodigy
Retrieval doesn't have to mean "vector DB." For a single uploaded document, direct parse-and-cite is simpler,
cheaper, and just as auditable as a full RAG pipeline - reserve vector search for when you're searching
across many documents or products.
Interview one-liner
"RAG is a spectrum from 'stuff the one document in context' to 'a full vector-search pipeline' - I pick the
simplest version that's still fully citable."

Vector databases - and when you don't need one
PLAIN ENGLISH
A vector database stores embeddings and answers "nearest neighbour" queries efficiently at scale
(millions of chunks). It's the retrieval substrate under large-scale RAG. But if your corpus is small,
structured, and already has a good ID (a specific blueprint, a specific product), a normal database
lookup beats a vector DB on cost, latency, and debuggability.

ANALOGY
You don't need a search engine to find a file in a folder you organized yourself - you need one when
you're searching across a warehouse of unlabelled boxes.
CONCRETE EXAMPLE
Prodigy doesn't need a vector database to answer "what's Regalia Gold's joining fee" - that's a direct,
ID-based lookup in Product Center / GitDB. A vector DB would only earn its keep if you were searching
semantically across hundreds of MITC documents or thousands of historical CRs.
In Prodigy
An honest architecture doc says what it doesn't need yet, not just what it has. Product Center's current
retrieval is direct, structured, and grounded - no vector DB in the stack, and that's the right call today.
Interview one-liner
"The best AI PM answer to 'why no vector DB' is often 'because we don't need one yet' - I'd rather defend that
than over-engineer."

Fine-tuning vs. prompting vs. RAG - a decision framework
WHAT EACH LEVER CHANGES, AND WHERE PRODIGY SITS

1. PROMPTING / SKILLS
 Try first
 Changes behaviour, per call
 Cheap, instant, auditable
2. RAG / TOOLS
 Add when facts are large/dynamic
 Injects fresh facts
 Prodigy is here
3. FINE-TUNING
 Last resort
 Changes weights, permanently
 Slow, costly, goes stale
Prodigy uses zero fine-tuning today - column 1 and 2 solve behaviour and facts without ever needing column 3.
PLAIN ENGLISH
Fine-tuning adjusts a model's weights on your examples to change its behaviour or style - it doesn't
teach it new facts reliably and it doesn't stay current. Prompting/skills shape behaviour per-call without
retraining. RAG/tools inject fresh, specific facts. The decision order is usually: try prompting + tools first
(cheap, fast, auditable); add RAG when facts are large or dynamic; reach for fine-tuning only when you
need a stable behaviour change that prompting can't reliably produce (a specific tone, a specific output
format, at high volume).
ANALOGY

Prompting is giving an employee instructions for today's task. RAG is giving them the reference binder.
Fine-tuning is sending them through months of retraining to change how they instinctively work -
expensive, slow, and the wrong first move for something instructions could fix.
CONCRETE EXAMPLE
"Make the change-request summary sound more like our compliance team's style" -> try a better
skill/prompt first. "The model needs Regalia Gold's current fee" -> that's RAG/tools, not fine-tuning
(fine-tuning would bake in a fee that's wrong the moment it changes). Fine-tuning would only earn
consideration if, at huge scale, prompting consistently failed to hold a specific output structure.
In Prodigy
Zero fine-tuning today, and that's correct: skills + tools + schema solve behaviour and facts without the cost,
staleness risk, and retraining overhead fine-tuning would add.
Interview one-liner
"I reach for prompting and tools first, RAG for facts, and fine-tuning last and rarely - most 'we need to
fine-tune' requests are actually a skill-design problem."

WHAT THE COORDINATION COST LOOKS LIKE
PRODIGY: ONE AGENT, ROUTED SKILLS
 One agent

 One trace, one blast radius

in the same room over a routine checkup.

Loop vs. graph engineering
PLAIN ENGLISH
The simplest agent shape is a single loop (think -> act -> observe -> repeat). As journeys get more 
complex, some teams model the flow as a graph - explicit nodes and edges representing states and 
transitions, useful when the same journey can branch, retry, or fan out in genuinely different ways. A

graph adds power and complexity; most journeys don't need one.
ANALOGY
A loop is a person walking a straight hallway, checking each door. A graph is a full building map with
marked shortcuts, locked doors, and alternate routes - useful for a building with real complexity,
overkill for a hallway.
CONCRETE EXAMPLE
Path 1 (launch) could be described as a graph: blueprint-confirm -> configure (which itself branches
into guided / upload / clone) -> CR -> dry run -> deploy. It's still simple enough to reason about as a
sequence with side branches, not a full state-machine graph engine.
In Prodigy
Prodigy's journeys are explicit sequential pipelines with named branches, not a generic graph-execution
engine - a deliberately simpler, more auditable choice for a regulated product.
Interview one-liner
"I know when a journey has earned a graph abstraction and when it's still just a sequence with branches -
most of ours are the latter, on purpose."
Prodigy-native
Sessions and auditability
PLAIN ENGLISH
A session is the bounded, persisted context for one conversation - bound to a specific tenant and 
verified user. In a regulated product, sessions double as a compliance surface: what was said, what

was proposed, what was confirmed, and by whom.
ANALOGY
A session is a case file, not a chat log - it's built to be re-opened by an auditor a year later, not just
re-read by the same user tomorrow.
CONCRETE EXAMPLE
If a regulator asks "who proposed the $150 annual fee and who confirmed it," session and thread
history should answer that without reconstructing anything from memory.
In Prodigy
Every session is bound to tenant and verified user, stored in Redis via the Agents SDK session mechanism -
not through Responses API conversation IDs, to keep one clear storage and audit boundary.
Interview one-liner
"Session design in a bank isn't a UX feature - it's the audit trail, so I treat it as a compliance requirement from
day one."

Prodigy-native
Hallucination and schema-as-law
PLAIN ENGLISH
Hallucination is a fluent, confident, false statement. It's not a bug you can fully eliminate - it's a risk you
design around. In a product with real consequences, the fix is structural: never let the model invent a
field name, an enum option, or a value that isn't backed by schema or a tool result.
ANALOGY
A very articulate intern who will confidently answer any question, correct or not, unless you hand them
the actual rulebook and tell them to quote it.
CONCRETE EXAMPLE
If Alex asks for a fee type that doesn't exist on this blueprint, the model must say "that option isn't
available on this product" - sourced from the schema's enum list - never invent a plausible-sounding
new fee type.
In Prodigy
Schema is law: fields, enums, and conditionals come from Product Center schemas and named operations -
never from the model's judgment about what "should" exist.

Interview one-liner
"We don't claim zero hallucination - we claim schema, tools, confirmation, and evals make harmful
hallucination a release-blocking defect."
Prodigy-native
Grounding, citations, and evidence
PLAIN ENGLISH
Grounding means every factual claim traces to a real source - a specific record, revision, or service
result - not to the model's memory. A citation is the pointer that lets a human verify the claim without
re-doing the work.
ANALOGY
A well-written research paper: every claim has a footnote. You don't have to trust the author's memory
- you can go check the footnote yourself.
CONCRETE EXAMPLE
"How has Regalia Gold's annual fee changed?" should answer with a timeline that cites specific GitDB
revisions, not a paraphrase from the model's general sense of what fees "usually" do.
In Prodigy
Every product-affecting claim cites a GitDB revision and field, or a named service result - Product Center
Service selects the required records; the model only gets what it needs, never raw unrestricted access.
Interview one-liner

"If a claim can't cite a GitDB revision or a service result, it doesn't ship as a fact in our product."
Prodigy-native
Guardrails - input, output, and action
WHAT THE THREE LAYERS LOOK LIKE AROUND ONE REQUEST
INPUT guardrail
uploaded MITC text is labeled untrusted data, never an instruction
the model reasons, drafts a proposal
OUTPUT guardrail
claims must cite a GitDB revision or service result
ACTION guardrail
entitlement parity - can only do what Alex's own UI allows
Three separate checkpoints. A model that somehow ignores the input guardrail still can't act outside the action guardrail - no
single point of failure carries the whole risk.
PLAIN ENGLISH
Guardrails constrain the model at three points: input (what untrusted content is allowed in, and how
it's labeled), output (what shapes/claims are allowed out), and action (what the model is actually
permitted to do, regardless of what it asks for). Entitlements are an action-level guardrail: the agent
can only do what the user's own UI access already allows.
ANALOGY
A bank teller: input guardrail (they don't take instructions from a note a stranger slips them), output
guardrail (they can't say things that violate disclosure rules), action guardrail (they physically cannot
open the vault, regardless of what anyone tells them).

CONCRETE EXAMPLE
MITC PDF text is an input guardrail case - it must never be treated as a trusted instruction, only as
data to extract from (prompt-injection risk). "Agent tools cannot approve or apply" is an action
guardrail, enforced regardless of what the model outputs.
In Prodigy
Entitlement parity - the agent can only do what the user's UI already allows - is the single most important
action guardrail in the whole system.
Interview one-liner
"I design guardrails at three separate points - what goes in, what comes out, and what's actually allowed to
happen - because a single filter isn't enough."

Eval design - the round that separates strong candidates from adequate ones
WHAT ONE EVAL RUN LOOKS LIKE
GOLDEN CONVERSATION (MUST HAPPEN)
 Given: partial blueprint, 3 fields empty
 Expect: calls get_schema, asks about exactly those 3
 Pass = matches expected tools + outcome
RELEASE-BLOCKING NEGATIVE (MUST NEVER HAPPEN)
 Given: PDF with injected instruction
 Must NOT: follow the injected instruction

Any violation blocks the release
A demo only proves the golden path once. Shipping requires both columns, every release, not just the happy path that worked
in front of the VP.
PLAIN ENGLISH
An eval is a systematic test of agent behaviour, not a demo. A strong eval suite has: golden
conversations (scripted happy paths with expected tools and outcomes), release-blocking negative
tests (things that must never happen - cross-tenant access, unauthorized tools, prompt injection,
stale-data writes, duplicate or concurrent-turn bugs), and increasingly LLM-as-judge scoring for
open-ended quality dimensions a simple string match can't capture, always anchored against a
human-reviewed reference. This is the round hiring managers say they can't safely shorten.
ANALOGY
A pilot's simulator check: it's not enough to fly well once on a sunny day. You test engine failure, bad
weather, and the exact scenario that grounded the last plane - every time, before every release.
CONCRETE EXAMPLE
A golden conversation for guided configuration: "given this blueprint and this partial state, the agent
must call get_schema, ask about exactly these 3 missing required fields, and never propose a value
for a field the schema marks read-only." A release-blocking negative: "given a prompt-injected
instruction inside an uploaded PDF, the agent must not follow it."
In Prodigy
Evaluation scores skill selection, authoritative retrieval, field mapping, evidence, deterministic validation,
explanations, and write controls separately - a good NLP summary can't compensate for a broken
write-control test. Reviewed production outcomes become regression test cases after approval and redaction.

This is the skill hiring panels probe hardest and PMs underinvest in most, because it's unglamorous
compared to roadmap and vision work. Owning the eval spec - not just the roadmap - is what separates an AI
PM from a PM who happens to ship AI features.

THE CORE JOB, REFRAMED
A traditional PM ships a button that either works or doesn't. An AI PM owns a product whose behaviour

sense under uncertainty, eval design, model trade-off judgement (quality vs. latency vs. cost), roadmap
calls that survive the next model release, and the willingness to say no to an LLM when a rules engine

PHASE 7 - INTERVIEW AMMUNITION

Speak Prodigy in agent vocabulary
Goal: 60-90 second answers. No fluff. No overclaim.
Ready spoken answers
1 - WHAT IS AN AGENT IN YOUR PRODUCT?
"In Prodigy an agent is a goal-seeking loop on the OpenAI Agents SDK that can call typed tools, observe
results, and continue under stop conditions. It is not a free-form chatbot with production keys. For configure,
the goal is a review-ready draft; tools load schema and lookups; writes wait for Alex to confirm; apply waits
for change request and human deploy."
2 - SKILL VS. TOOL VS. MCP?
"A skill is a versioned procedure with confirmation points - how to run blueprint or guided configure. A tool is
a typed function in ToolRegistry that hits the same application services as REST. MCP is the protocol so an
external harness can discover and call those tools over Streamable HTTP with OAuth - not a second
source of truth and not approve/apply."
3 - WHY NOT LET THE AGENT DEPLOY?
"Because blast radius in issuer product config is institutional. We separate propose, form truth, CR
validation, dry run, and human deploy. Agent adapters intentionally expose read, validate, and propose
only. That's how we stay bank-grade without pretending the model is a release manager."
4 - HOW DO YOU STOP HALLUCINATIONS?
"Schema is law. Lookups come from list APIs. Empty or error means we say so. Citations for Q&A come
from GitDB or service results. Document extractors show a confirm board. Evals include release-blocking
negatives for invented options, cross-tenant access, and writes before confirm."
5 - CHATBOT VS. AGENT - HOW DID YOU DECIDE?
"Cited fee questions are chat plus read tools. Validation is a deterministic workflow. Launch-from-MITC is
agentic because language and multi-step tools matter - but still human-in-the-loop. I use a simple test: is
the path fixed, is the write dangerous, is language the interface?"

6 - MULTI-AGENT - DID YOU NEED IT?
"We bias to a single embedded agent with routed skills: create 24205, update 24213, ask 24214, clone
24207. Multi-agent is on the table for isolation or parallel specialists, but each added loop costs latency and
failure modes. I won't add agents for resume keywords."
7 - TELL ME ABOUT EVALS.
"Each skill gets golden conversations - expected tools and outcomes. Release blockers include
cross-tenant, unauthorized tools, prompt injection via uploads, stale revisions, and pre-confirm mutation.
Validation engine results are not 'LLM judged' into green."
8 - BUILD VS. BUY FOR THE HARNESS?
"We buy model access and an Agents SDK/runtime via Azure Foundry rather than training a foundation
model. We build the product contracts: skills, ToolRegistry, entitlements parity, CR integration, and UX.
Differentiation is the control plane for issuer products, not the base model."
9 - HOW DOES PAGE-AWARE CONTEXT WORK?
"The base passes page, product, blueprint, active tab, and session into skills so Alex doesn't restate the
screen. That's context engineering as a product feature - it reduces tokens and errors versus
megaprompts."
10 - SOFT FAILURE MODE?
"If Prodigy is unavailable, Product Center forms and existing CR/deploy workflows still operate. AI is an
acceleration layer on the system of record, not a fork of it."
Frameworks to keep in your pocket
Build vs. buy
Buy: models, Agents SDK, Foundry hosting. Build: skills, tools, entitlements, CR glue, evals, UX. Buy
commodity intelligence; build the control plane.
Agent vs. workflow

Agent when language -> multi-step tools under uncertainty. Workflow when pass/fail must be identical and
auditable. Hybrid is normal.
